# Завдання 2. Робочий застосунок: прототип → БД

Складено AI з моїх відповідей ([ai/prompts/02-prototype-db.md](../../ai/prompts/02-prototype-db.md)), погоджено мною.

## Що і навіщо

Сценарії зі [spec.md](../../spec.md) працюють через HTTP API: спершу на
статичних даних у пам'яті, потім на PostgreSQL за тим самим API. Один набір
API-тестів проганяється на обох сховищах, тож заміна статики на БД
перевіряється, а не декларується.

## Сценарії та очікувана поведінка

Користувач-ініціатор приходить у заголовку `X-User-Id` (заглушка BankID).
Business-process ID береться з `X-Request-Id` або генерується, повертається
в тому ж заголовку й потрапляє в кожен рядок логу.

```http
GET  /cycles                      200 раунди з поточною фазою
POST /cycles                      201 раунд з лімітами категорій        admin
GET  /cycles/:id                  200 раунд, ліміти, фаза
GET  /cycles/:id/projects         200 заявки з автором і кількістю голосів
POST /cycles/:id/projects         201 заявка (сценарій 1)                resident
GET  /projects/:id                200 заявка і рішення модератора
POST /projects/:id/review         201 рішення (сценарій 2)               moderator
POST /projects/:id/votes          201 голос (сценарій 3)                 resident
GET  /me/votes?cycleId=           200 мої голоси в раунді
POST /cycles/:id/tally            200 підсумки (сценарій 4)              admin
GET  /cycles/:id/results          200 підсумки з назвами проєктів
POST /projects/:id/progress       201 звіт про реалізацію (сценарій 5)   admin
GET  /projects/:id/progress       200 звіти про реалізацію
GET  /health  /ready  /version    живість, доступність БД, sha збірки
```

Кількість голосів видно й під час голосування. Повторний голос за той самий
проєкт дає 409. Подання і звіт з тим самим `Idempotency-Key` повертають уже
створений запис (200), повторний підрахунок дає той самий результат.

Статичні дані містять кілька раундів у різних фазах (подання, модерація,
голосування, завершений), щоб кожен сценарій можна було пройти на демо.

## Схема БД і запити

Схема в [migrations/](../../migrations/): сутності з ER у spec.md; `votes`
PK (voter_id, project_id), `reviews.project_id` унікальний,
`(author_id, idempotency_key)` унікальний у `projects` і `progress_reports`,
`max_cost <= budget`, гроші `bigint` у копійках.

Ключові запити: голос у транзакції `SERIALIZABLE` (голоси виборця в раунді →
вставка) з повтором на `40001`/`40P01`; рішення модератора оновлює статус і
вставляє Review в одній транзакції; голоси раунду рахуються одним `GROUP BY`;
пов'язані записи списку (автори, проєкти) читаються одним запитом `= any($ids)`.

## Сценарії помилок

| Ситуація | Статус | `error` |
|---|---|---|
| Тіло чи параметри не за схемою | 400 | `validation_failed` |
| Немає або невідомий `X-User-Id` там, де потрібен | 401 | `unauthenticated` |
| Не та роль | 403 | `forbidden` |
| Немає раунду чи проєкту | 404 | `not_found` |
| Повторний голос, повторне рішення модератора, ключ повтору з іншим тілом | 409 | `conflict` |
| Порушено правило: фаза, ліміт, вартість, порожня причина | 422 | код правила |
| БД недоступна або не відповідає вчасно (запит довше 5 с, блокування довше 2 с) | 503 + `Retry-After` | `source_unavailable` |
| Будь-що інше | 500 | `internal` |

Тіло помилки завжди `{ error, message, bpId }`; формує його один глобальний
обробник.

## Критерії прийняття

| ID | Критерій | Перевірка |
|---|---|---|
| AC-2.1 | Усі сценарії з таблиці API проходять через HTTP спершу на статичних даних, потім на PostgreSQL, тим самим набором тестів | тест |
| AC-2.2 | 5 одночасних голосів виборця при `max_votes = 2` дають рівно 2 записи | тест |
| AC-2.3 | Повторне подання з тим самим `Idempotency-Key` не створює дубля; той самий ключ з іншим тілом дає 409 | тест |
| AC-2.4 | Без БД сервер не стартує і пояснює чому; якщо БД впала під час роботи, API відповідає 503, `/ready` 503, а після відновлення працює без перезапуску | тест |
| AC-2.5 | Кожен рядок логу з роуту, сервісу й репозиторію містить bpId і користувача без передачі параметром | тест |
| AC-2.6 | SQL і транзакції є лише в `*/repository.pg.js` і `src/platform/db`; роути й сервіси їх не бачать | `npm run lint`, `npm run boundaries` |
| AC-2.7 | Помилки з таблиці мають свій статус і тіло `{ error, message, bpId }` від одного глобального обробника | тест |
| AC-2.8 | Рішення модератора атомарне: збій посеред транзакції не лишає ні статусу, ні Review | тест |
| AC-2.9 | Тести працюють на окремій базі на кожен прогін; локальний PostgreSQL слухає 55432, не 5432–5434 | тест |
| AC-2.10 | Списки заявок і підсумків роблять однакову кількість запитів при 7 і 17 елементах; кількість є в лозі запиту (додано за аудитом, п. 1) | тест |
| AC-2.11 | Якщо таблицю тримає блокування іншої транзакції, запит отримує 503 менш ніж за 4 с, а не чекає (додано за аудитом, п. 2) | тест |
| AC-2.12 | Кожне `check`-обмеження схеми має пару в домені: той самий запит дає той самий статус на обох сховищах (додано за аудитом, п. 3) | тест |
