# Завдання 4. CI/CD і розгортання

Складено AI з моїх рішень ([ai/prompts/04-cicd.md](../../ai/prompts/04-cicd.md), P2), погоджено мною.

## Що і навіщо

Зараз мердж у `main` можливий з червоним CI, розгортання немає. Потрібні
CI, що блокує мердж, і автодеплой кожного коміту в `main` на публічний
стейдж.

## Перевірки CI

На кожен PR і кожен пуш у `main`:

| Задача | Що перевіряє | Обов'язкова для мерджа |
|---|---|---|
| `check (ubuntu-latest)` | стиль, лінт, типи, межі модулів, усі тести на PostgreSQL, `npm pack` | так |
| `commits` | кожен коміт PR має формат conventional commits (commitlint) | так |
| `build` | `docker build`; контейнер проти PostgreSQL CI мігрує, `/ready` = 200, `/version` = sha | так |
| `check (windows-latest)` | те саме на Windows | ні |
| `mutation` | mutation score ≥ 70% (Завдання 3) | ні |

Той самий commitlint працює локально в хуку `commit-msg`.

## Політика мерджа

`main` захищена: лише через PR; три обов'язкові перевірки зелені на
останньому коміті; гілка актуальна з `main`; без прямого пушу й
force-push; адміністратор правил не обходить.

## Ціль CD

Стейдж: Render Free (Docker-образ) + Neon Free (PostgreSQL).

Після зеленого CI на `main` задача `deploy`:

1. збирає образ і пушить у GHCR з тегом = sha коміту;
2. викликає deploy hook Render з `imgURL` цього тегу;
3. чекає, поки `/version` стейджу поверне цей sha (з повторами: Free
   засинає); за 10 хв не дочекалась — падає.

Раннер CI не знає адреси БД стейджу (вона лише в Render) і не має SSH;
єдиний секрет у GitHub — deploy hook.

## Міграції без простою

Один образ і один entrypoint для стейджу й проду:

1. `migrations/schema/` — зміни структури, блокуючі, у транзакції з
   `lock_timeout`;
2. `migrations/data/` — оновлення даних, окремим кроком після схеми;
3. сервер стартує і відповідає на `/health`;
4. `migrations/indexes/` — фонова задача після старту: `CREATE INDEX
   CONCURRENTLY` під advisory lock, без таймауту старту; недобудований
   індекс перестворюється.

Seed окремо від міграцій: лише за `SEED=1` (тільки на стейджі), повтор
нічого не дублює.

Зміна схеми сумісна з попередньою версією коду (розширити → перейти →
прибрати).

## Blue-green

Нова версія не отримує трафік, поки `/ready` ≠ 200; `/ready` = 200, коли
схема й дані змігровані і БД доступна. На SIGTERM `/ready` одразу дає 503,
сервер доробляє поточні запити і закриває пул. Доказ — тест AC-4.7: дві
версії за проксі, перемикання під навантаженням.

На стейджі (Render Free) zero downtime немає: під час деплою короткий
простій. На платному плані проду механізм той самий, `/ready` — health
check Render.

## Аудит

Один PR, де коміти по черзі ламають і лагодять кожну обов'язкову
перевірку (стиль, лінт, тест, повідомлення коміту, Dockerfile); для
кожного — посилання на червоний прогін і доказ, що мердж заблоковано.

## Поза межами

Продакшн (механізм той самий); платні функції Render; фонові оновлення
даних.

## Критерії прийняття

| ID | Критерій | Перевірка |
|---|---|---|
| AC-4.1 | CI на кожен PR запускає стиль, лінт, тести, білд образу і перевірку комітів | тест (конфігурація CI) |
| AC-4.2 | Мердж у `main` заблоковано, поки `check (ubuntu-latest)`, `commits` і `build` не зелені; прямий пуш і force-push заборонено, адмін не обходить | `npm run ci:protection`, аудит |
| AC-4.3 | Коміт з повідомленням не у форматі conventional commits відхиляє і хук `commit-msg`, і задача `commits` | тест |
| AC-4.4 | Контейнер з образу застосовує міграції на старті і віддає `/ready` = 200 проти чистої БД | `npm run test:container` |
| AC-4.5 | Міграції схеми, даних і індексів — окремі теки й кроки; індекси будуються після старту, не блокуючи `/ready` | тест |
| AC-4.6 | Seed виконується лише за `SEED=1` і не дублює дані при повторі | тест |
| AC-4.7 | Під час перемикання двох версій за проксі жоден запит не падає | тест |
| AC-4.8 | Коміт у `main` після зеленого CI автоматично розгортається на стейдж; задача `deploy` падає, якщо `/version` стейджу не повернув sha цього коміту | тест, прогін CI |
| AC-4.9 | Стейдж доступний з інтернету: `/ready` = 200, список раундів відповідає, `/version` повертає sha задеплоєного коміту | `npm run stage:check` |
