# Завдання 1. Фундамент: специфікація інкременту

## Що і навіщо

Закласти репозиторій і власні інженерні стандарти на весь курс, спроєктувати
структуру застосунку ([spec.md](../../spec.md)) і зібрати конвеєр, який не
пропускає брудний код ні в коміт, ні в push. Каркас модулів виводиться зі
spec.md, щоб наступні завдання нарощували код у вже обґрунтованих межах.

## Критерії прийняття

| ID | Критерій | Перевірка |
|---|---|---|
| AC-1.1 | На чистому клоні `make setup` і `make check` завершуються з кодом 0 | `make check` |
| AC-1.2 | pre-commit відхиляє коміт, якщо staged-код не відформатований або не проходить лінтер; чистий коміт проходить | тест |
| AC-1.3 | pre-commit перевіряє знімок індексу: неіндексована брудна правка не блокує чистий коміт, а брудний staged-файл блокує навіть після виправлення в робочій копії | тест |
| AC-1.4 | pre-push відхиляє push, якщо не проходить `make check` (типи, тести, збирання пакета) | тест |
| AC-1.5 | `GET /health` повертає 200, `GET /version` повертає sha поточного коміту | тест |
| AC-1.6 | Теки модулів `src/*` точно збігаються з таблицею модулів у spec.md | тест |
| AC-1.7 | Правила сценаріїв 1–4 зі spec.md реалізовані чистими функціями без БД і покриті тестами | тест |
| AC-1.8 | spec, ADR і DEFENSE відповідають своїм стандартам, у кожного критерію є перевірка | `make docs` |
| AC-1.9 | Правила меж R1, R2, R4 зі spec.md перевіряються для кожного модуля зі spec; порушення блокує коміт (додано за аудитом, п. 1) | `make boundaries`, тест |
