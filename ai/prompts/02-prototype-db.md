# Завдання 2. Прототип → БД: промпти

Порядок роботи за DoD (повна версія з AI, §1): AI аналізує вимоги й ставить
уточнювальні питання, рішення ухвалюю я, далі AI виконує за spec.
Мої повідомлення наведено дослівно; питання AI скорочено до суті.

## P1. Постановка (я, 27.10)

Дав AI повний текст Завдання 2 з Classroom і шаблон DEFENSE.

<details><summary>Дослівно</summary>

```text
Мета: реалізувати основні сценарії спершу на статичних даних, потім замінити
реальною роботою з БД.

Що зробити:
• spec.md: сценарії та очікувана поведінка; схема БД, запити, сценарії помилок.
• Прототип на статичних даних (без БД): основні сценарії через зовнішній
  інтерфейс — HTTP API (або UI-виклики). API покриває ВСІ основні сценарії,
  а не один GET; схема БД без API прототипом не вважається.
• Інтеграція БД: замінити статику реальною БД; транзакції, валідація,
  обробка збоїв джерела, ідемпотентність/ретраї.
• Рівні декомпозиції: роути знають про HTTP; сервіси — про бізнес-операції
  й доступи; SQL і транзакції — лише в репозиторіях/DAO. SQL чи транзакції
  в роутах — порушення меж.
• Керування залежностями: без протягування 10–15 параметрів. Щонайменше:
  ініціалізовані ресурси (БД), користувач-ініціатор, business-process ID, що
  автоматично потрапляє в кожен лог з будь-якого рівня. Варіанти: DI,
  context-реєстр, AsyncLocalStorage / contextvars, Effect тощо — вибір в ADR.
• Обробка помилок: один глобальний обробник, а не try/catch на все тіло
  кожної функції.
• Аудит: топ-3 зрізані кути / крайові випадки; N+1 (де виникла і як
  виправлено); поведінка на збоях.
• DEFENSE.md + adr/ на вибір БД/ORM і керування залежностями.

Рекомендації: пул БД — явна ініціалізація на старті + SELECT now() (падати
одразу); ізольоване локальне середовище (не 5432/5433/5434 на localhost;
окрема база на прогін/гілку); одна стратегія розміщення моделей; SQL tagged
templates для сирого SQL.
```

</details>

## P2. Питання AI і мої відповіді (27.10)

AI поставив 12 питань; нижче питання коротко, відповідь дослівно.

| # | Питання AI | Моя відповідь |
|---|---|---|
| 1 | Які сценарії мають працювати через API? | «сценарії що мають працювати через апі створення раунду, подання проєкту, модерація, голос, підсумки, звіт про реалізацію, плюс перегляд списків» |
| 2 | Хто користувач-ініціатор у прототипі? | «`X-User-Id` користувач ініціатор» |
| 3 | PostgreSQL чи SQLite; чи є Docker? | «PostgreSQL»; «я скачаю докер» |
| 4 | Сирий SQL чи ORM? | «сирий SQL через бібліотеку `postgres` (tagged templates, як радить завдання» |
| 5 | Як передавати БД, користувача, bpId? | «користувача й bpId без протягування параметрів: AsyncLocalStorage, DI-контейнер»; на уточнення: «Контейнер робимо бібліотекою `awilix`» |
| 6 | Makefile чи `npm run`? | «DoD каже, що для Node він не потрібен і так і є» |
| 7 | Повторний голос: 200 чи 409? | «409» |
| 8 | Показувати голоси під час голосування? | «показуй кількість голосів поки голосування триває» |
| 9 | Як пройти всі фази на демо? | «Робимо в тестових даних кілька раундів у різних фазах» |
| 10 | Що робити, коли БД впала? | «відповідати 503 і відновлюватися без перезапуску» |
| 11 | Критерії готовності? | взяв запропоновані AI варіанти як основу (див. нижче) |
| 12 | Що поза межами? | не відповів; у spec — варіант AI (логін/BankID, пагінація, UI), на погодження |

Критерії готовності, які я затвердив:

```text
* усі сценарії проходять через API спершу на статичних даних, потім на
  PostgreSQL, тим самим набором тестів;
* 5 одночасних голосів при ліміті 2 дають рівно 2;
* повторне подання з тим самим `Idempotency-Key` не створює дубля;
* без БД сервер не стартує, а якщо БД впала під час роботи, відповідає 503 і
  сам відновлюється;
* кожен рядок логу містить bpId і користувача, а в роутах немає SQL.
```
