# Зберігати дані в PostgreSQL через сирий SQL бібліотеки postgres

## Контекст і проблема

Прототип на статичних даних треба замінити справжньою БД. Сценарії мають
транзакції з умовою (не більше `max_votes` голосів на раунд при одночасних
запитах), ідемпотентне подання і підсумки, що перезаписуються атомарно.
Завдання радить пул з перевіркою на старті й сирий SQL на tagged templates.

## Чинники рішення

* рівень ізоляції транзакцій має бути керованим (`SERIALIZABLE` для голосу);
* SQL видно в коді репозиторію, без магії ORM, і він параметризований;
* одна стратегія моделей: доменні типи в `domain.js`, рядки БД мапляться
  лише в `repository.pg.js`;
* запуск на Windows студента без складного налаштування.

## Розглянуті варіанти

* PostgreSQL + бібліотека `postgres` (tagged templates)
* PostgreSQL + `pg` (node-postgres) з ручними `$1`-параметрами
* PostgreSQL + Prisma
* SQLite + `better-sqlite3`

## Рішення

Обрано: «PostgreSQL + бібліотека `postgres` (tagged templates)», бо
``sql`select … where id = ${id}` `` параметризує значення сам (SQL-ін'єкція
неможлива за побудовою), `sql.begin('isolation level serializable', …)`
дає транзакцію з потрібним рівнем ізоляції, а пул і `select now()` на
старті — це одна функція `connectDb`.

### Наслідки

* Добре, бо обмеження живуть у схемі БД (PK голосу, унікальний ключ
  повтору, `max_cost <= budget`), а не лише в коді.
* Добре, бо конкурентні голоси коректні: `SERIALIZABLE` + повтор на
  `40001`/`40P01` у `platform/db/tx.js`.
* Погано, бо міграції пишемо самі (`migrations/*.sql` + маленький мігратор),
  без відкату.
* Погано, бо на Windows потрібен Docker Desktop або інсталятор PostgreSQL.

### Підтвердження

Той самий набір API-тестів проходить на PostgreSQL (AC-2.1); тест
одночасних голосів (AC-2.2); `npm run lint` забороняє SQL поза
`*/repository.pg.js` і `src/platform/db` (AC-2.6).

## Плюси й мінуси варіантів

### `pg` (node-postgres)

* Добре, бо найпоширеніший драйвер.
* Погано, бо параметри `$1, $2` пишуться вручну і легко розходяться з
  масивом значень; транзакції — вручну через `BEGIN`/`COMMIT` на клієнті.

### Prisma

* Добре, бо типізовані запити й міграції з коробки.
* Погано, бо модель живе в `schema.prisma`, а не в модулі-власнику, і
  рівень ізоляції та умовні вставки під контролем ORM, а не нашим SQL.

### SQLite + `better-sqlite3`

* Добре, бо один файл, нічого не ставити на Windows.
* Погано, бо один записувач на базу: одночасні голоси не перевіряють те,
  що буде в продакшені, і рекомендації завдання (пул, `SELECT now()`,
  окремий порт) до нього не застосовні.
