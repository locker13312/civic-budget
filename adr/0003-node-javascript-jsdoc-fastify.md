# Використовувати Node.js 22, JavaScript з типами в JSDoc і Fastify

## Контекст і проблема

Курс вимагає JavaScript. Потрібен стек для вебсервісу з БД, який дає суворі
перевірки (типи, лінтер, межі модулів) і при цьому лишає код
JavaScript-кодом.

## Чинники рішення

* код має лишатися JavaScript, який запускається без компіляції;
* помилки типів мають ловитися до запуску, а не в продакшені;
* валідація HTTP-запитів має бути частиною фреймворку, а не ручною.

## Розглянуті варіанти

* JavaScript + JSDoc, перевірка `tsc --checkJs`, Fastify
* TypeScript + NestJS
* JavaScript без перевірки типів + Express

## Рішення

Обрано: «JavaScript + JSDoc, перевірка `tsc --checkJs`, Fastify», бо файли
лишаються `.js` і запускаються напряму в Node.js, а `tsc` у режимі `strict`
перевіряє типи з JSDoc так само суворо, як у TypeScript. Fastify перевіряє
тіла запитів за JSON Schema і має `inject()` для тестів без мережі.

### Наслідки

* Добре, бо немає кроку компіляції: що в репозиторії, те й працює.
* Добре, бо `node:test` вбудований у Node.js 22, для тестів не потрібна
  окрема бібліотека.
* Погано, бо JSDoc багатослівніший за синтаксис TypeScript.
* Погано, бо `tsc` потрібен як dev-залежність лише заради перевірки.

### Підтвердження

`make types` запускає `tsc --noEmit` з `checkJs` і `strict`; `npm ci` у
`make setup` падає, якщо `package-lock.json` не відповідає `package.json`.

## Плюси й мінуси варіантів

### TypeScript + NestJS

* Добре, бо типи в синтаксисі мови і готова модульна структура.
* Погано, бо це вже не чистий JavaScript, а модульність NestJS тримається
  на DI-контейнері, а не на перевірці імпортів.

### JavaScript без перевірки типів + Express

* Добре, бо найпростіший старт.
* Погано, бо помилки типів видно лише під час виконання, а валідацію
  запитів Express лишає на розробника.
