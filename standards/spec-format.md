# Стандарт: формат spec

## Навіщо

Spec фіксує, що будуємо і як зрозуміти, що збудовано. Працюємо з AI, тому
spec одночасно є задачею для AI: чого в ній немає, того AI не зробить або
зробить на свій розсуд.

## Два види spec

| Вид | Файл | Скільки | Обов'язкові розділи |
|---|---|---|---|
| Системна | `spec.md` | одна, живий документ | Що і навіщо · Компоненти і взаємодія · Дані · Сценарії оновлення даних · Правила меж |
| Інкремент | `tasks/NN-назва/spec.md` | одна на завдання | Що і навіщо · Критерії прийняття · Поза межами |

## Правила

1. Обсяг: не більше однієї сторінки, тобто 600 слів без урахування блоків
   коду й діаграм. Не вміщається, значить інкремент завеликий: ділимо.
2. Критерії прийняття оформлюються таблицею `ID | Критерій | Перевірка`.
   ID має вигляд `AC-<номер завдання>.<номер>`, унікальний і не
   перевикористовується після видалення критерію.
3. Критерій описує спостережуваний результат: код повернення, відповідь
   ендпоінта, стан даних. Слова «зручно», «швидко», «якісно» без числа
   заборонені.
4. Колонка «Перевірка» містить `тест` (тоді існує тест, у назві якого є
   `[AC-N.k]`) або npm-скрипт у зворотних лапках (`npm run x`).
5. Spec інкременту комітиться до коду, який її реалізує: у історії гілки
   коміт зі spec іде першим. Критерії, змінені після аудиту, змінюються
   окремим комітом з посиланням на пункт аудиту.
6. Розділ «Поза межами» обов'язковий: явно сказати, чого не робимо, корисніше
   для AI, ніж ще один критерій.

## Як перевіряється

`npm run docs` (скрипт `scripts/check-docs.js`): наявність розділів, ліміт слів,
формат і унікальність ID, для кожного критерію існує тест з маркером або
npm-скрипт. Правило 5 перевіряється на рев'ю за історією PR.
